FS261 | API resource design and contracts | junior
Q: An order API accepts one POST /doEverything request for creation, cancellation, and address changes. How would you improve its contract?
A: Model operations around an order resource and its lifecycle. Define separate creation, address update, and cancellation operations with explicit eligibility rules. Choose HTTP methods by their semantics. Document request fields, response shapes, status codes, and repeated-request behavior. Keep state transitions in the service layer so another transport cannot bypass the same business rules.

FS262 | API resource design and contracts | junior
Q: A client requests a new customer record. When should the API return 201, 202, or 200?
A: Return 201 when creation has completed, normally including the resource representation or its location. Return 202 when work has only been accepted and provide a way to inspect its eventual outcome. Use 200 for successful operations such as queries or updates returning content. Asynchronous language features inside a handler do not themselves justify 202.

FS263 | API resource design and contracts | junior
Q: A PATCH request omits phoneNumber while another explicitly sends null. What should the contract specify?
A: Define omission as leaving the field unchanged and null as clearing it only if clearing is permitted. Use a patch-specific schema rather than treating the request as a complete replacement. If using JSON Merge Patch, follow its null-removal semantics. Test omitted, null, empty-string, and valid-value cases so serializers cannot silently change the intended meaning.

FS264 | API resource design and contracts | mid
Q: A public API must rename customerName to displayName without immediately breaking consumers. What rollout would you suggest?
A: Introduce the new field while retaining the old one during an announced transition. Define write behavior when both appear; reject contradictory values rather than guessing. Update schemas and examples, measure adoption, and communicate a deadline. Remove the old field through the agreed breaking-change mechanism. Even additive changes need review when consumers reject unknown fields.

FS265 | API resource design and contracts | mid
Q: Why can offset pagination repeat or skip orders during a busy day, and what alternative would you offer?
A: Concurrent inserts and deletions shift row positions between requests. Cursor pagination instead continues after a stable ordering tuple such as createdAt and id. Include a unique tie-breaker, bound page sizes, and bind the cursor to its ordering context. This improves traversal stability but does not automatically provide a frozen snapshot of changing records.

FS266 | API resource design and contracts | junior
Q: A search endpoint supports many filters and sort fields. How do you keep its contract predictable?
A: Publish allowed filters, operators, and sort keys with clear defaults and limits. Specify how multiple filters combine and how empty values behave. Map public names to predefined query expressions instead of exposing arbitrary database expressions. Return consistent errors for unsupported combinations. Add a stable tie-breaker to ordering so pagination does not depend on accidental row order.

FS267 | API resource design and contracts | mid
Q: A bulk update of 100 products finds three invalid entries. Should the other 97 be updated?
A: Either atomic processing or partial success can be valid, but the contract must choose explicitly. Atomic processing suits shared invariants. Partial success needs an outcome for every item, stable correlation identifiers, and clear retry rules. Limit batch size before processing. A single success flag must not conceal partial failure or encourage retries of already-completed changes.

FS268 | API resource design and contracts | junior
Q: An invoice-generation operation takes two minutes. How should clients discover whether it completed?
A: Create a durable job resource and return 202 with its status location. Expose queued, running, succeeded, and failed states, plus a result link when available. Provide reasonable polling guidance and define cancellation and retention. Progress must survive the original connection ending; an HTTP timeout cannot be the only record of the operation's outcome.

FS269 | API resource design and contracts | junior
Q: Should a product endpoint expose its database entity directly to avoid mapping code?
A: Usually prefer an explicit response model. Entities may contain internal fields, persistence relationships, or columns that evolve independently of the public contract. Response models make supported fields intentional and reduce accidental disclosure and over-fetching. Mapping costs some maintenance, but separates schema changes from consumer compatibility. Keep the mapping straightforward rather than introducing an elaborate framework.

FS270 | API resource design and contracts | mid

Add semantic descriptions, examples, and contract checks for important responses. Review schema changes during code review. A syntactically valid specification does not prove that an API is usable or backward compatible.

Prefer a correlated NOT EXISTS for anti-join intent, or explicitly remove nulls when that matches the model. Understand whether null represents missing data rather than treating it as an ordinary comparable value.

FS320 | SQL query semantics | junior

Choose based on whether duplicates represent valid separate facts or repeated representations of the same fact. Deduplication also adds work. Do not use UNION merely as a default when combining event sources; equal projected values may still correspond to distinct legitimate events.

FS331 | Transactions and concurrency | junior
Q: A transfer debits one account and credits another across separate autocommit statements. What can go wrong?
A: A failure between statements can leave money debited without the corresponding credit. Wrap both updates in one transaction so they commit or roll back together. Define behavior when the operation retries, detect already-applied transfers idempotently, and validate balances under the chosen isolation model. FS332 | Transactions and concurrency | junior
Q: What does a rollback guarantee after an error inside a transaction?
A: It discards uncommitted changes made during that transaction, restoring database-visible state to its prior point. It does not reverse external side effects such as sent emails, published messages, or files already written. Design around this by sequencing external actions after commit or compensating deliberately. Database state and the outside world are not covered by one atomic boundary.

FS333 | Transactions and concurrency | mid
Q: Two agents read the same product stock, then both decrement and save. What anomaly occurs and how can it be prevented?
A: This is a lost update: one decrement silently overwrites the other. Options include atomic conditional updates such as UPDATE ... WHERE stock >= requested, selecting rows for update, optimistic version checks that fail concurrent writes, or serializable isolation. Choose based on contention, latency, and engine support. Verify the chosen mechanism with a concurrency test rather than assuming the ORM prevents this pattern.

FS334 | Transactions and concurrency | mid
Q: An inventory report needs consistent totals while orders keep arriving. How can snapshot semantics help?
A: A transaction-level snapshot lets related reads observe one consistent database version while other transactions commit. A statement-level snapshot alone does not guarantee agreement across multiple report queries. Check the engine's isolation behavior and configure the required scope. Long snapshots can delay version cleanup and consume storage, so bound report duration and avoid assuming every default read mode offers identical guarantees.

Q: Why is a distributed transaction across two independent services generally avoided, and what replaces it?
A: Coordinated two-phase commit couples availability across services and complicates every participant, so many designs prefer eventual consistency: one service owns the state change, publishes events, and others react idempotently with compensation when later steps fail. This accepts temporary inconsistency in exchange for independence. Choosing between them depends on business requirements for atomicity versus availability and operational maturity.

FS478 | Distributed systems and consistency | mid
Q: A downstream consumer processes events out of order. What design options exist?
A: Include version numbers, sequence numbers, or timestamps in events and let consumers discard or reorder stale updates. Some brokers support partitioning by key so related events arrive in order. Alternatively, design consumers to be order-insensitive by reading authoritative state after notification. Event ordering assumptions must be explicit, because silent out-of-order processing corrupts projections and creates intermittent, confusing defects.

FS479 | Distributed systems and consistency | mid
Q: What is a saga, and how does it handle a step failing midway?
A: A saga coordinates a multi-step business process across services as a sequence of local transactions, each with a defined compensating action if a later step fails. Compensation is semantic undo, like cancelling a reservation, not necessarily reversing the underlying operation. Sagas trade atomicity for availability and need careful state tracking, retry policy, and observability to remain debuggable.

FS480 | Distributed systems and consistency | mid
Q: Why do distributed clocks complicate event ordering across services?
A: Wall clocks differ between machines and can step backward, so timestamps alone cannot establish causal order. Use logical clocks, sequence numbers, or dependency tracking where ordering matters, or route related events through a single ordered channel. Accept that perfect global ordering may be unnecessary; identify which decisions actually require it rather than assuming every event stream needs strict global sequencing.

Q: How would you identify whether a slow endpoint is limited by database, application logic, or external calls?
A: Measure where time goes: application timing around each stage, database query durations and plans, and external call latency. Tracing across boundaries shows which dominates. Profile representative traffic rather than a single warmup request. Each cause has different remedies: indexing and query changes for database work, algorithmic improvement for logic, and caching or timeouts for external dependencies.

FS482 | Scalability and performance | mid
Q: Why can adding more application instances fail to improve throughput?
A: If the bottleneck is a shared database, a single-threaded dependency, lock contention, or external rate limits, extra instances add load without adding capacity. Profile the whole path before scaling horizontally. Confirm that connection pools, queue consumers, and caches actually distribute work. Scaling the tier that is not saturated wastes cost and may worsen database contention through more concurrent connections.

FS483 | Scalability and performance | junior
Q: What are the tradeoffs of loading a full user profile on every request versus lazy loading parts of it?
A: Full loading simplifies code and guarantees consistency within a request but wastes work when only a few fields are needed. Lazy or field-specific loading reduces transfer and computation but increases query counts and risks N+1 patterns. The right choice depends on access patterns, sizes, and latency budgets. Profile before optimizing; premature splitting adds complexity without measurable benefit.

FS484 | Scalability and performance | junior
Q: What is connection pooling, and what happens with too few or too many pooled connections?
A: Pooling reuses database connections instead of opening one per request, avoiding expensive handshakes. Too few connections serialize work and build queues; too many exhaust database capacity and increase contention, degrading all clients. Size pools against the database's capacity and workload characteristics, monitor wait times, and ensure pool settings are coordinated across all instances sharing one database.

FS485 | Scalability and performance | mid
Q: A report performs CPU-heavy calculations and delays unrelated API requests. What isolation options help?
A: Move expensive computation to a bounded worker pool or separate process, depending on the runtime. Limit queued work and reject or defer excess demand rather than spawning unlimited tasks. Separate compute-heavy jobs from latency-sensitive request capacity. Measure CPU saturation and scheduling delays; asynchronous syntax does not make CPU work nonblocking or create additional processor capacity.

FS486 | Scalability and performance | mid
Q: A growing events table is difficult to maintain. How does partitioning differ from sharding?
A: Partitioning divides a logical table into manageable pieces, often within one database, enabling pruning and lifecycle operations when queries and partition keys align. Sharding distributes data across independent database nodes and adds routing, rebalancing, and cross-shard coordination. Neither automatically accelerates every query. Choose based on measured capacity or maintenance needs rather than table size alone.

FS487 | Scalability and performance | mid
Q: What problems come from storing large binary blobs directly in a relational table?
A: Rows become heavy, slowing scans, backups, replication, and even queries that exclude the blob column depending on storage layout. Memory pressure rises when clients fetch wide rows. Object storage with a metadata row referencing the object usually scales better, keeps databases lean, and enables direct client uploads or downloads. Smaller inline blobs may be acceptable when access patterns truly require transactional coupling.

FS488 | Scalability and performance | junior
Q: Why does a missing LIMIT on an internal admin search cause production incidents?
A: Unbounded queries return entire tables, exhausting memory, saturating network, and blocking database resources while other queries wait. Apply limits everywhere, including internal tools and scripts, and bound offsets or require explicit filters. Add statement timeouts where supported to prevent runaway queries from holding connections indefinitely. Review arbitrary admin queries with the same rigor as customer-facing endpoints.

FS489 | Scalability and performance | mid
Q: How can read replicas help a reporting workload, and what limitations apply?
A: Replicas offload heavy reads from the primary, but replication lag means reported data may be behind writes. Queries that were fine on the primary can still consume replica resources and affect other reads. Route queries that tolerate staleness to replicas and keep strong-consistency reads on the primary, with monitoring for lag. Replicas also provide failover candidates but do not substitute for backups.

Fairness may reduce peak throughput for the busiest tenant, so align scheduling policy with service commitments.

A: Compare database-side signals such as query duration, lock waits, connection saturation, and replication lag against application-side signals like thread pool exhaustion, garbage collection, and downstream call latency. Correlation across the request path matters: a slow query shows in database metrics; slow serialization shows only in application timing. Distributed tracing often resolves the ambiguity fastest.
